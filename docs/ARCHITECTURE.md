# Architecture

RaftLab separates the protocol from everything uncertain about the world. The core depends on six interfaces (transport, clock, log store, state machine, timeouts, randomness). The simulator, the TCP transport, the WAL, the fault matrix and the clock are implementations of those interfaces, and the checkers watch from the side without taking part in any decision.

## Module map

```
internal/raft/         election, replication, persistence, snapshots, membership, invariants
internal/storage/      WAL with CRC32-C frames, in-memory store for tests
internal/sim/          virtual clock, scheduler, network, cluster, fault matrix, event log
internal/transport/    Transport over real sockets, same fault-control surface
internal/check/        client history, KV model, order and bitmask searches
internal/unsafe/       names for the eight broken variants
cmd/raftlab/           CLI and the gates
cmd/importcheck/       import graph enforcement
docs/PROGRESS.md       raw gate output, regenerated by scripts/gates.sh
reports/failures/      shrunk failing seeds
```

## Components

- `raft.Node` is one node's state machine. `Step` is the only entry point: timers, RPCs and client proposals all arrive there. There are no goroutines inside the node and no locks, because there is nothing concurrent to protect.
- `sim.Scheduler` owns the event heap. Timeouts are scheduled clock events rather than timers, so time only moves when the scheduler says it does.
- `sim.Network` applies drop, delay, duplicate and partition rules, then enqueues delivery.
- `sim.Cluster` wires nodes, network, clock and monitor into one scenario and records a client history.
- `raft.Monitor` evaluates invariants from the same event stream.
- `check` records client operations as intervals and decides whether the history is linearizable.
- `storage.WAL` frames records as magic, kind, length, CRC32-C and payload, so a torn tail is recoverable and a bad checksum is loud.

## Event flow

1. The scheduler pops the next event and advances the virtual clock to it.
2. A timer event becomes `MsgTickElection` or `MsgTickHeartbeat` and is stepped into the node.
3. The node sends through its transport, and the network decides whether to drop, delay, duplicate or reorder the message before delivering it.
4. The observer records state changes, sends, persists, log appends and applies. The monitor checks invariants on those same events.
5. The event log is canonicalised and hashed. Two runs of the same seed must produce the same hash.

## Decisions worth knowing

Dependencies point one way. The node cannot see the simulator, and the import graph is enforced by `cmd/importcheck` and by a test inside the package.

Each actor derives its own random stream from the seed. Adding a node does not shift the streams of the nodes that were already there, which keeps old replays valid.

Liveness is reported, not asserted. A precise timing assertion on a simulated scheduler is a reliable way to write a test that fails for reasons unrelated to the protocol.

An invariant that fires changes the protocol. The invariant is not edited to accommodate the implementation.

A gate that fails stops the milestone. The evidence is a raw transcript in `docs/PROGRESS.md`, produced by `scripts/gates.sh`.

## Known trade-offs

The eight broken variants are wired into the core through `Config.Bug`. This keeps one code path under one simulator, at the cost of test-only branches inside the shipped node. The alternative, variant wiring behind a hook interface, has not been implemented.

Six of the sixteen fault kinds are declared and not wired. `WiredFaults` and `UnwiredFaults` in `internal/sim/faults.go` are the contract, and a test asserts the split.

Both linearizability searches share one KV model. Their agreement rules out a search bug, not a modelling bug.
